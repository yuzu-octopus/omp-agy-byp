# omp ↔ Antigravity signature mapping — research synthesis

Date: 2026-11-18. This report synthesizes four findings files in this directory. No secret values (OAuth client secret, tokens, credential paths) are reproduced; only public identifiers and source anchors are cited.

**Release update:** Google published [Antigravity CLI 1.5.11](https://github.com/google-antigravity/antigravity-cli/releases/tag/1.5.11) on November 18, 2026, after this snapshot. References to 1.5.10 below describe the earlier evidence; no compatibility check was run against 1.5.11.

## Answer

Four questions were investigated. The short answers:

1. **Header/TLS spoofing — path-dependent.** On the primary `antigravity-cli` / `antigravity-acp` path, omp emits **no HTTP headers, User-Agent, or Authorization header at all**: there is no `fetch`/header construction in that transport, and the native `agy` subprocess owns the socket, TLS stack, headers and identity. So there is nothing for omp to spoof on this path, and no extension surface from which to do it. On the **direct CCA path** (`google-antigravity` / `google-gemini-cli`), omp *does* clone native-looking HTTP headers (User-Agent, Client-Metadata, Accept-Encoding, Accept) with env overrides and live manifest version discovery — but it uses Bun's global `fetch`, so **TLS/JA3/JA4/HTTP2 fingerprinting is not spoofed** on either path. ([F-header-tls.md](F-header-tls.md), Verdict)

2. **429 / key rotation / bans — the user claim is half-confirmed.** It is **confirmed by primary first-party repository docs that some proxies rotate/fail over to other keys or accounts on 429**: gcli2api rotates `(OAuth credential, GCP project)` units on `401/403/429/5xx`; OmniProxy switches accounts only on subscription **capacity-exhausted** 429 (ordinary API-key 429 stays project-shared and does not iterate accounts). **agy2api is different**: it applies model-family cooldown on 429 with configurable credential selection modes (`random`/`cache`/`sticky`), not 429-triggered key failover (`F-quota-rotation.md` C1–C3). It is **not supported by any primary source that those rotation patterns are what triggers a Google ban**; the mechanism is plausible and consistent with documented enforcement and observability, but no detector name, signal, threshold or rotation-to-ban rule is published. Separately, **omp's built-in `antigravity-cli` path has no rotation at all** — it holds one credential envelope per account and stages one token file, so the rotation-correlated anomaly vector is structurally absent (429 is a hard stop). ([F-quota-rotation.md](F-quota-rotation.md), D6/E3)

3. **agy version / identity — pinned one release behind.** Latest public CLI is **1.5.10** (published 2026-11-17); the binary is closed-source. Installed omp 18.22.2 hard-codes a **1.5.9** roster. Genuine-client identity surfaces (ACP `clientInfo`/`agentInfo`, model gating, MCP naming, auth methods) are documented, but the upstream HTTP User-Agent and TLS fingerprint are not. ([F-antigravity-latest.md](F-antigravity-latest.md), F1/F10)

4. **omp → agy signature mapping — best-effort only.** The only loop-safe rewrites are system-prompt *text* (and, lower value, tool descriptions). Detection from specific system-prompt identity lines is **documented by a first-party relay A/B (S10)**: Claude Code billing lines, Claude Agent SDK identity lines, Codex GPT-5 identity lines and Hermes Agent persona lines in the system prompt trigger upstream `400 prompt_turned_away`/`Resource has been exhausted`, and rewriting those lines returns `200`. That is relay-reported evidence, not a Google publication, and it did not test omp's own markers or tool names; omp-specific scrubbing remains untested. The mapping therefore establishes *reachability* for omp's markers, not omp-specific *efficacy*. Everything that is a dispatch id, resource scheme, transport meta key, credential, or fingerprint is a hard contract that must be preserved verbatim. ([F-signature-map.md](F-signature-map.md), Summary/Risks)

## Confidence

- **High** (source/doc directly observed): the ACP path emits no omp headers/TLS; the direct CCA path clones headers but not TLS; gcli2api and OmniProxy rotate identities on 429, agy2api uses cooldown plus configured credential selection (first-party repo docs); 429/`RESOURCE_EXHAUSTED` semantics and Google quota/retry guidance; Google bans third-party proxy quota access (maintainer posts + ToS); omp's single-credential CLI architecture; omp pins agy 1.5.9 while latest public is 1.5.10; the reachability of the three model-visible content surfaces and the hard-preserve contracts.
- **Medium** (inferred or relay-reported): consumer Antigravity quota-group shape (relay docs, not Google); that a single key lowers a header/TLS-mismatch signal; proxy config defaults carried via the companion evidence file; practitioner-reported ACP identity strings.
- **Low / speculative**: the claim that rotation *patterns* specifically cause bans; all inferred anomaly signals (switch cadence, IP/ASN change, prompt-cache reuse, header/TLS mismatch); efficacy of scrubbing omp's own markers/tool names (S10 tested other clients' identity lines, not omp's); closed-CLI ACP internals on the installed 1.5.9 build: CHANGELOG 1.5.10 documents wait-and-retry up to 4 min on per-minute rate/capacity limits (implying a >30 s stop in 1.5.9), but the 1.5.9 ACP path is untested (F-quota-rotation.md E5).
- **Overall**: high for "proxies rotate on 429" and "Google bans third-party proxy quota access"; **low** for "rotation is the detected pattern that triggers the ban" and for "scrubbing omp's own markers/tool names changes detection"; the S10 relay A/B raises confidence for detection from the specific system-prompt identity lines it tested, but it is not a Google publication and does not cover omp markers.

## Findings

### Header/TLS

- **ACP path (`antigravity-cli` / `antigravity-acp`):** `streamAntigravityCli` stages a credential file and spawns `agy acp`, communicating over stdio NDJSON plus a loopback MCP server — no `fetch`, no `RequestInit`, no header construction ([F-header-tls.md](F-header-tls.md) F1). `resolveHeaders` only resolves model metadata; the `headers`/`authHeader` knobs affect HTTP-backed providers, not this ACP transport. `onPayload`/`onResponse` (`before_provider_request`/`after_provider_response`) are set in provider options but never read by this transport, so rewrite hooks cannot reach it (F1). Env knobs are binary/state/auth only (`PI_AGY_PATH`, `AGY_CLI_DISABLE_AUTO_UPDATE`, `SSH_TTY`); no header or TLS overrides (F2). omp cannot tune the upstream fingerprint from source: whatever the backend sees is the native `agy` binary's.
- **Direct CCA path (`google-antigravity` / `google-gemini-cli`):** both share one stream, branched by `model.provider` ([F-header-tls.md](F-header-tls.md) F3). It clones native headers — Antigravity UA `antigravity/hub/<version> (aidev_client; os_type=…; arch=…; cl=…)`, Gemini CLI UA + `Client-Metadata`, `Accept-Encoding: gzip`, and an explicit `Accept` on the Gemini branch — with overrides `PI_AI_ANTIGRAVITY_VERSION`, `_CL`, `_OS`, `_ARCH`, `PI_AI_GEMINI_CLI_VERSION` (F4). Assembly adds the real OAuth Bearer token and lets `...options.headers` override any field (F4).
- **TLS gap:** requests use Bun's global `fetch` (with `timeout: false`), not Go `net/http`; the source comments explicitly note header strings mimic the Go client while the TLS ClientHello is still Bun's. No JA3/JA4/uTLS/ClientHello machinery exists in this path (the TLS-profile code present in the repo is Anthropic/Cursor-scoped) ([F-header-tls.md](F-header-tls.md) F5). Google's edge can compute `tls_ja3_fingerprint`/`tls_ja4_fingerprint`, but no public Google doc ties these to Gemini subscription enforcement.

### 429 / rotation / bans

- **429 semantics (documented):** canonical code `RESOURCE_EXHAUSTED` = 8; `PERMISSION_DENIED` must not be used for exhaustion; `UNAVAILABLE` is the transient retry code ([F-quota-rotation.md](F-quota-rotation.md) A1–A2). Google's own AIP-194 guidance calls `RESOURCE_EXHAUSTED` "generally non-retryable" — multi-key 429 failover deliberately overrides that guidance (A3). Two distinct 429 causes exist: short-window rate limiting vs exhausted quota (A4); quota is scoped per-project and per-credential/user (B1–B4).
- **Proxies do rotate on 429 (confirmed, first-party repo docs):** gcli2api rotates `(OAuth credential, GCP project)` units on `401/403/429/5xx` with **no exponential backoff** (C1); OmniProxy rests a **subscription capacity-exhausted** account for the reset window and switches accounts when alternatives exist, while ordinary API-key 429 stays project-shared and does **not** iterate accounts (C3); agy2api applies **model-family cooldown** on 429 with `RETRY_429_ENABLED` default true and credential-select modes `random`/`cache`/`sticky` — it is not 429-triggered key failover (C2). Google itself lists spreading workloads across distinct service accounts as a per-user-429 resolution (C5, scope-limited).
- **Bans are documented, rotation-to-ban is not:** Google's 2026-02-27 announcement tied a ban wave to third-party tools/proxies accessing Antigravity resources and quotas, with enforcement shared across services and recertification requirements ([F-quota-rotation.md](F-quota-rotation.md) D1); a 2026-03-18 maintainer post announced more robust detection of third-party OAuth use and account-standing-based traffic priority (D2); Antigravity Additional ToS clause 6 prohibits third-party software/tools/services access and permits suspension/termination (D3). Google can attribute a 429 to a `credential_id` (OAuth client ID) and to a quota project, so correlation infrastructure exists (D4). **No primary source states that rotating keys on 429 is itself a detection trigger, or names any scored anomaly signal** (D5). Verdict: half-confirmed — (a) rotation on 429 confirmed, (b) rotation-patterns-cause-bans plausible but unproven (D6).
- **omp CLI path has no rotation:** one structured credential envelope per account; per stream a single native token file is staged with file-only auth; a token refresh restarts the host but does not switch accounts ([F-quota-rotation.md](F-quota-rotation.md) E1–E3). On 429 there is no second key to fail over to, so no rotation cadence is emitted. Trade-off: avoids one candidate signal but makes quota exhaustion a hard stop; native headers/UA/TLS are fixed in the installed source and not reachable by hooks (E4). Whether the closed `agy acp` binary internally retries on 429 is unverified (E5).

### agy version / identity

- Latest public CLI = **1.5.10** (published 2026-11-17); repo publishes docs/changelog/examples only — binary closed-source ([F-antigravity-latest.md](F-antigravity-latest.md) F1). omp 18.22.2 hard-codes a **1.5.9** roster, one release behind (F1, F6).
- Official `agy acp` surface: JSON-RPC over stdio, ACP protocol v1, self-identifies as `Antigravity ACP Server`; flags include `--add-dir`, `--agent`, `--sandbox`, `--ide-mcp-port`, `--login`, `--disable-telemetry` (F2). `clientInfo`/`agentInfo` name/title/version are SHOULD, not MUST; `_meta` is the extension channel (F3).
- **Model gating changed:** pre-1.5.1 server offered Claude/GPT-OSS only to allowlisted `clientInfo.name` values (jetbrains, android-studio, zed, xcode); changelog 1.5.1 offers every account-available model to every ACP client ([F-antigravity-latest.md](F-antigravity-latest.md) F3; practitioner repros A1). Whether the allowlist was fully removed remains an open question.
- **MCP bridge:** `--ide-mcp-port` requires `nc`; eager tools are `mcp_<serverName>_<toolName>`, lazy tools via `call_mcp_tool` (F4). omp's loopback bridge advertises `serverInfo {name:"tools",version:"1.0.0"}` (F4). System prompt is shipped as `_meta.antigravity.systemPrompt.append`, not as prompt text (F5) — an undocumented protocol-extension behavior.
- **Auth/client identity:** five auth methods; keyring with SSH fallback; public installed-app OAuth client with secret stored base64 in source (value never reproduced here); token in a private account-scoped file (F8). omp's argv is fixed and its ACP `clientInfo.name` is `bridge`, with fs/terminal capabilities false ([F-antigravity-latest.md](F-antigravity-latest.md) F9). Upstream HTTP UA/TLS are owned by the closed CLI with no public spec; omp emits zero headers on this path (F10).

### omp → agy mapping

- Only **three model-visible content surfaces** exist on the CLI path: joined system prompt (as ACP `_meta`), tool name/description/schema (as `mcp_ide-tools_<name>`), and messages/context ([F-signature-map.md](F-signature-map.md) scope). Reachable seams are `before_agent_start`, `context`, and registerTool/setActiveTools; provider request/response hooks are ignored here.
- **Safe rewrites are text only:** role line, skills heading/prose, internal-URLs prose, `xd://` device prose, tool-inventory label, condensed tool-policy prose, persona names, delegation prose (R1–R9 in [F-signature-map.md](F-signature-map.md)). Keep `skill://<name>`, `xd://<tool>`, tool ids, and scheme strings verbatim; drop a skill entry rather than rename it.
- **Hard preserves:** built-in tool ids, `mcp__<server>_<tool>` and `mcp_ide-tools_<name>` prefixes, internal URL schemes, `agy_<uuid>` call ids, `antigravityCli` payload fields, `systemKey`/`toolsKey` stability (rewrite only at a turn boundary), ACP `_meta` keys, fixed argv/env, OAuth credentials, and all HTTP header/UA/TLS/CCA fields (Hard preserves in [F-signature-map.md](F-signature-map.md)).
- **Efficacy unproven:** a first-party relay A/B (S10) documents upstream identification of specific system-prompt identity lines in other clients and an outcome change when those lines are rewritten; there is no Google publication and no A/B covering omp's own markers or tool names, so scrubbing those remains speculative mitigation. The map establishes reachability and carries the S10 signal only by analogy, not omp-specific efficacy (Risks/Q1–Q2). Header/UA/TLS spoofing from an extension is structurally impossible on this path.

## What would change this

- A **traffic capture / instrumented black-box test** of the closed `agy acp` binary (1.5.9 and 1.5.10) showing its actual TLS/HTTP2 fingerprint and whether entitlement is bound to it would resolve the ACP-path fingerprint question and confirm the 1.5.9 internal-429-retry behavior that CHANGELOG 1.5.10 only implies (F-quota-rotation.md E5).
- A **primary Google source** naming a consumer-Antigravity detection signal, threshold, or a rotation-to-ban rule (or a documented ban count attributable to rotation) would upgrade the half-confirmed ban claim; its absence is what keeps it low-confidence.
- **Empirical detector probing on omp's own markers**: the S10 relay A/B already demonstrates this for other clients' system-prompt identity lines; a controlled A/B on omp's role line, tool names and `mcp_ide-tools_` prefix would move the signature map from borrowed evidence to omp-specific efficacy.
- Confirmation of whether the **`clientInfo.name` allowlist was fully removed in 1.5.1** (official issue #1318 is still open), and the exact wire semantics of `_meta.antigravity.systemPrompt.append`, would firm up the identity mapping.
- Evidence that **`options?.fetch` or `options?.headers` are set by any real omp caller** would change the direct CCA path's TLS/header conclusion.
- Alignment of omp's pinned **1.5.9** roster with 1.5.10 (or proof 1.5.10 changed ACP `_meta`, tool naming, or auth) would update the version/identity findings.

## Considered and rejected

- **Spoofing headers/TLS on the ACP path via a `PI_AGY_PATH` shim.** Mechanically possible but rejected: it skips SHA-512 verification and discards the genuine signed-CLI fingerprint that is the provider's structural advantage, for no measured gain ([F-signature-map.md](F-signature-map.md) Hard preserves; [F-header-tls.md](F-header-tls.md) F2).
- **Treating prompt/tool scrubbing as a proven bypass.** Rejected as a claim: detection from those content surfaces is documented only by a first-party relay A/B for specific other-client identity lines (S10), not by a Google publication, and not for omp's markers or tool names; the work is best-effort only (Risks/Q1–Q2).
- **Assuming `before_provider_request`/`after_provider_response` rewrite headers on the CLI path.** Rejected: those hooks are set but never read by `streamAntigravityCli`; assuming they fire yields a silent no-op ([F-header-tls.md](F-header-tls.md) F1).
- **Upgrading "proxies rotate on 429" to "rotation causes bans."** Rejected as unsupported; the causal mechanism has no primary evidence ([F-quota-rotation.md](F-quota-rotation.md) D5–D6).
- **Credential rotation as an omp mitigation or risk.** Not applicable on the built-in CLI path: a single credential envelope means no key pool to rotate (E3).
- **TLS/HTTP2 spoofing on the direct CCA path.** Not present in source; the Go-vs-Bun split is deliberate-but-partial (header strings only), and JA3/JA4 remain Bun's ([F-header-tls.md](F-header-tls.md) F5).

## Open questions

- Does the closed `agy` binary present Google's exact first-party TLS/HTTP2 fingerprint, and is entitlement bound to it? (needs binary/traffic capture)
- Does Google score 429-triggered identity switching, cross-account prompt-cache reuse, IP/ASN spread, or header/TLS mismatch on consumer Antigravity? No public documentation; unanswerable from primary sources today.
- Does the installed `agy acp` 1.5.9 internally retry, back off, or rotate on 429? CHANGELOG 1.5.10 documents wait-and-retry up to 4 min on per-minute rate/capacity limits and implies a >30 s stop in 1.5.9; the 1.5.9 ACP path is untested and cannot be settled from omp source (F-quota-rotation.md E5).
- Do multiple subscription accounts sharing one OAuth client ID or quota project expand usable quota, or only shuffle denials?
- Did 1.5.1 fully remove the `clientInfo.name` allowlist, or only widen the model catalog? (issue #1318 still open)
- What are the exact wire semantics of `_meta.antigravity.systemPrompt.append` (append vs replace; loadSession vs newSession precedence), and would relabeling change prompt-cache prefixes?
- On the HTTP fallback, what is the full `CloudCodeAssistRequest` field inventory needed to rewrite labels/requestId safely?
- Do image-generation, quota and usage side requests run through `antigravity-acp` or only HTTP providers?
- Does `options?.fetch`/`options?.headers` get set by any real omp caller, changing the direct path's fingerprint?
- Is the manifest-discovered direct-path version (`ensureAntigravityVersion`) in sync with the 1.5.9 CLI binary used by the ACP path?
