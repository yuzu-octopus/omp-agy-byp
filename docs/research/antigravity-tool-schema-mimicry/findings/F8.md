# F8 — Reconciliation: shadow tools vs provider-internal reverse mapping

## Angle

Settle the F3/F4 (provider-internal reverse map at `toMcpTool` + `#onToolCall`) vs F5 C15/C37 (extension-reachable shadow tools + `tool_call`/`execute` translation) tension. One question: does "agy sees an Antigravity-like surface" preserve "omp sees canonical tool ids/calls"? All installed sources are omp 18.22.2 (`@oh-my-pi`); paths below are relative to that package root. Fetch date for every source: **2026-11-18**. Confidence: `primary` = direct read; `inference` = primary lines chained.

## Claims

### 1. Identity recorded at the provider seam

- **C1 FACT primary.** The name omp records is the raw MCP name, with no reverse map: bridge `tools/call` looks up `byName.get(params.name)` and calls `onCall(tool.name, args, conversationId)` (`pi-ai/src/providers/antigravity-cli/mcp-bridge.ts:159-160,180`); advertised name is `tool.name` (`toMcpTool`, `host.ts:858`); `AgyHost.#onToolCall` writes `step.writer.toolCall({type:"toolCall", id, name, arguments: args})` with that same `name` (`host.ts:626,629,665`). Date 2026-11-18.
- **C2 FACT primary.** `StepWriter.toolCall` pushes the call object itself into `output.content` and emits `toolcall_start/delta/end` carrying it (`pi-ai/src/providers/antigravity-cli/step-writer.ts:74-88`). The `ToolCall.name` in the omp assistant message is therefore whichever name arrived from the bridge. Date 2026-11-18.
- **C3 FACT primary.** The digest is computed over that exact content: `transcriptDigest([...step.messages, step.writer.output])` (`host.ts:667`), where `messageContent` hashes `{type:"toolCall", id, name, arguments}` (`pi-ai/src/providers/antigravity-cli/reconcile.ts:165-183`, esp. :177-178), and `transcriptDigest` is sha256 of stable-stringified message content (`reconcile.ts:76-83`). The resulting digest is written into the `antigravityCli` payload (`host.ts:668`) and ledger (`:669`). Date 2026-11-18.
- **C4 FACT primary.** The tool-call id is omp-minted and stable: `agy_${crypto.randomUUID()}` (`host.ts:656`), stored as `pendingToolCallId` (`:669`) and required for resume (`reconcile.ts:47-55`). Shadow tools change the *name* identity, not this id. Date 2026-11-18.

### 2. What every omp layer sees under shadow tools

- **C5 FACT/inference primary chain.** Under `registerTool` + `setActiveTools` shadow design, the advertised name is the shadow name (C1), so `step.writer.toolCall` (`host.ts:665`), the assistant `ToolCall.name` (`step-writer.ts:78`), and the hashed digest (C3) all carry the **shadow** name. The canonical original is deactivated, so nothing rewrites it back. Date 2026-11-18.
- **C6 FACT primary.** The finalized assistant message is pushed into agent context (`pi-agent-core/src/agent-loop.ts:2374,2427-2429`) and persisted by the session store (`pi-coding-agent/src/session/agent-session.ts:4414-4430`, append at :4427). Session history therefore contains the shadow name. Date 2026-11-18.
- **C7 FACT primary.** TUI/transcript rendering reads the same name: `tool_execution_start/end` and `ToolResultMessage.toolName` use `toolCall.name` (`agent-loop.ts:3534-3564`), transcript cards resolve a renderer via `getTool(content.name)` and `toolRenderName(wireName, tool) = tool?.name ?? wireName` (`pi-tui/src/chat/chat-transcript-builder.ts:486-494,577-583`; `pi-tui/src/chat/tool-execution.ts:72-75`). With a shadow tool registered under the shadow name, TUI shows the shadow name; no canonicalization occurs. Date 2026-11-18.
- **C8 FACT primary.** Approvals key off the dispatched tool object, i.e. the shadow: `resolveApproval` uses `tool.name` as the settings key (`pi-coding-agent/src/tools/approval.ts:366-375,392-424`, esp. :401-408), ACP permission wrapping checks `PERMISSION_REQUIRED_TOOLS[tool.name]` and `userPolicies[tool.name]` (`pi-coding-agent/src/session/session-tools.ts:1213-1223`); `legacyName` only inherits `deny`/`prompt` (`pi-coding-agent/src/extensibility/extensions/types.ts:1053-1055`; `approval.ts:410-423`). Date 2026-11-18.
- **C9 FACT/inference primary chain.** Consequence of C5-C8: shadow tools achieve agy-facing shape but **omp's TUI, transcript, session store and approval keys all use the shadow identity**. The brief's "omp keeps canonical identities" is not met; only `agy_<uuid>` ids stay omp-native (C4). Date 2026-11-18.

### 3. Is `toolName` mutable in `tool_call` events?

- **C10 FACT primary.** Event shapes expose `toolName` as a field only: extension `ToolCallEventBase`/`CustomToolCallEvent` (`pi-coding-agent/src/extensibility/extensions/types.ts:1552-1600`), hook `ToolCallEvent` (`pi-coding-agent/src/extensibility/hooks/types.ts:312-320`), result events (`extensions/types.ts:1602-1653`; `hooks/types.ts:325-391`). Date 2026-11-18.
- **C11 FACT primary.** Handler result shapes contain no name: `ToolCallEventResult = {block?, reason?, input?, additionalContext?}` (`pi-coding-agent/src/extensibility/shared-events.ts:341-375`) and `ToolResultEventResult = {content?, details?, isError?, additionalContext?}` (`:414-435`); hooks re-export the same types (`hooks/types.ts:426`). Date 2026-11-18.
- **C12 FACT/inference.** Consumers never re-read the event object for a name: loop path builds the event inline with `toolName: ctx.tool.name` and reads back only `block`, `input`, `additionalContext` (`agent-session.ts:5928-5950`); wrapper path emits `toolName: this.tool.name` (`pi-coding-agent/src/extensibility/extensions/wrapper.ts:306-320`). `runner.emitToolCall` passes the event by reference to handlers (`runner.ts:2332-2379`) but aggregates only the result fields above. Mutating `event.toolName` inside a handler is inert — no rename reaches dispatch, persistence or TUI. Date 2026-11-18.

### 4. Can a shadow `execute` call canonical tools and keep canonical transcript name?

- **C13 FACT primary.** `ToolDefinition.execute(toolCallId, params, signal, onUpdate, ctx)` has no name parameter; `label`/`name` are static definition fields (`extensions/types.ts:1018-1067`, esp. :1019-1024,1060-1067). Date 2026-11-18.
- **C14 FACT/inference.** `execute` runs only after the provider step finalized: `finish("toolUse")` pushes `done` (`host.ts:668`; `step-writer.ts:109-117`), which resolves the stream result (`pi-ai/src/utils/event-stream.ts:218-248`), which the agent loop consumes before preparing dispatch (`agent-loop.ts:2352,2401-2405`) and executing tools (`:3382-3388`). Digest, payload and ledger are already fixed (C3). Calling the canonical tool from a shadow `execute` is a later nested dispatch; it cannot rewrite the already-emitted `ToolCall.name`. Date 2026-11-18.
- **C15 FACT/inference.** Any post-emission rewrite of that name breaks `transcriptDigest` equality: `planTurn` requires `transcriptDigest(messages.slice(0, ledger.count)) === ledger.digest` for resume/restore (`reconcile.ts:39-70`, :43 and :63). Verdict for (3): **no** — canonical behavior can be delegated, canonical *name in transcript* cannot. Date 2026-11-18.

### 5. Correction to F5 C15/C37: `tool_call` input revision is also a digest hazard here

- **C16 FACT/inference primary chain.** `beforeToolCall` (the loop bridge to extension `tool_call`) fires in `prepareToolCallDispatch` (`agent-loop.ts:3205-3211` → `agent-session.ts:5928-5936`) and bakes a revised input back into `toolCall.arguments` (`agent-loop.ts:3226-3234`). That runs **after** host computed the digest (`host.ts:667`) and wrote the payload (`:668`) — the loop only reaches `prepareToolCallDispatch` on the `done` event (`agent-loop.ts:2352,2401-2402`). `messageContent` hashes `arguments` (`reconcile.ts:178`). So F5's recommended "reverse translate args in `tool_call`" changes the persisted transcript without updating `antigravityCli.digest` → resume/restore fails and omp replays as fresh text (`reconcile.ts:43,63,72`; `host.ts:258,267-276`). Reverse translation must be deterministic *before* `step.writer.toolCall`, or must not touch hashed fields. Date 2026-11-18. Confidence: inference over primary anchors.
- **C17 FACT/inference.** Same timing invalidates any alias trick via `resolveFallbackTool`: the loop canonicalizes an unresolved name at `agent-loop.ts:3157-3164` (`:3162-3163`), also after the digest. Additionally that fallback resolves only `xd://`/`mcp__` spellings (`pi-coding-agent/src/sdk.ts:4232-4267`) and requires the canonical tool to remain advertised (`:4250-4255`), which agy would also see (`host.ts:222,858`) — defeating the alias. Date 2026-11-18.

### 6. Extension-reachable aliasing alternatives — all dead or insufficient

- **C18 FACT primary.** `customWireName` exists on `pi-ai` `Tool` (`pi-ai/src/types.ts:1739-1763`) but is absent from extension `ToolDefinition` (`extensions/types.ts:1018-1067`), and agy's `toMcpTool` emits only `tool.name` (`host.ts:858`). It cannot change the agy-facing name on this path. Date 2026-11-18.
- **C19 FACT primary.** `registerTool` exposes name/description/parameters/approval only; `hidden` and `defaultInactive` select roster membership, not wire naming (`extensions/types.ts:1018-1043`; `loader.ts:399-400`). Date 2026-11-18.
- **C20 FACT/inference primary chain.** Other candidate hooks are unreachable or post-digest: `transformProviderContext` has no extension registration path (F5 C28), `before_provider_request`/`after_provider_response` options are dropped by `streamAntigravityCli` (F5 C22-C24), `registerCustomApi` is blocked for built-in `antigravity-acp` (F5 C21), `assistant_message`/`context` rewrites desync the digest (F5 C17/C33; C16 here). Date 2026-11-18.

### 7. Self-consistency of the shadow fallback

- **C21 FACT/inference.** A stable shadow roster keeps `toolsKey = stableStringifyJson(tools)` constant (`host.ts:222-224`), so no process restart or parked-turn abandonment (`host.ts:227-249`) and no digest drift — provided the shadow name/schema never changes mid-session and no hashed field is rewritten post-emission (C16). Approval policy must be authored on the shadow name (C8); `legacyName` inherits only restrictive policies (`approval.ts:410-423`). Date 2026-11-18.

## Verdict

**No.** Shadow tools do not satisfy the brief's canonical-identity requirement: agy sees the alias, but `step.writer.toolCall`, omp transcript, TUI, session store and approval keys all record the shadow identity (C5-C9); `toolName` is not mutable (C10-C12), `execute` is too late (C13-C15), and extension arg rewrites desync the digest (C16). No extension-reachable technique aliases outbound and reverse-maps inbound before emission (C17-C20). Only a provider-internal adapter — wrap `toMcpTool` (`host.ts:854-859`) to alias outbound, wrap `#onToolCall` before `step.writer.toolCall` (`host.ts:626-672`, esp. :665) to map back, keeping name/args stable for `toolsKey`/digest — preserves canonical omp identity; that requires host-source modification (F3 C14, F4 C18). **Honest fallback** if source cannot be changed: shadow tools with fully omp-visible shadow identity, stable shapes, shadow-keyed approvals, and no post-emission rewriting of hashed fields (C21).
