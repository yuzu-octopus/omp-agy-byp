## Claims

- **C1 — ACP is JSON-RPC 2.0 between Client (editor/host) and Agent; v1 is stable, v2 is Draft.** Client initializes → capabilities/auth → `session/new` → `session/prompt` → `session/update` stream → response with stopReason. Fixed method names and JSON-RPC envelope are spec JSON-RPC 2.0; custom methods MUST start with `_`; ACP keys camelCase, discriminator string values snake_case. Source: `https://agentclientprotocol.com/protocol/v1/overview.md` (Overview, Conventions, Extensibility); `https://agentclientprotocol.com/llms.txt`. Fetch 2026-11-18. **[PRIMARY]**
- **C2 — `protocolVersion` is a single integer MAJOR version (`uint16`, 0–65535).** Client MUST send its latest; Agent MUST answer with the requested version or its own latest; Client SHOULD disconnect on an unsupported version. v1 examples use `1`; v2 uses `2`. v2 adds strict validation (`-32022` Unsupported protocol version, `data.requested`/`data.supported`) and permits repeated `initialize` before the first other request — v1 does not define this. Source: `https://agentclientprotocol.com/protocol/v1/initialization.md` §Protocol version/Version negotiation; `https://agentclientprotocol.com/protocol/v2/initialization.md`; `schema/v1/schema.json` `$defs.ProtocolVersion` (`type: integer, format: uint16, minimum 0, maximum 65535`). Fetch 2026-11-18. **[PRIMARY]**
- **C3 — ACP pins `1`, so v1 shapes apply to the `agy acp` path.** Installed host calls `connection.initialize({ protocolVersion: 1, clientCapabilities: { fs: { readTextFile: false, writeTextFile: false }, terminal: false }, clientInfo: { name: "bridge", title: "Host tool bridge", version: "1" } })`. No elicitation, no other client capability is advertised from this bridge. Source: installed `pi-ai/src/providers/antigravity-cli/host.ts:444-450` (also `:281` newSession). Fetch 2026-11-18. **[PRIMARY]**
- **C4 — The tool-call wire shape is fixed by a closed `sessionUpdate` discriminator.** v1 `SessionUpdate` oneOf consts include `"tool_call"`, `"tool_call_update"`, `"user_message_chunk"`, `"agent_message_chunk"`, `"agent_thought_chunk"`, `"plan"`, `"available_commands_update"`, `"current_mode_update"`, `"config_option_update"`, `"session_info_update"`, `"usage_update"`, `"notice"`, `"compaction_update"`, `"compaction_summary_chunk"`. These strings, and the JSON-RPC method `session/update`, cannot be renamed without leaving the spec. Source: `schema/v1/schema.json` `$defs.SessionUpdate` (discriminator `sessionUpdate`); `https://agentclientprotocol.com/protocol/v1/tool-calls.md` Creating/Updating. Fetch 2026-11-18. **[PRIMARY]**
- **C5 — v1 `ToolCall` requires only `toolCallId` and `title`.** All of `name`, `kind`, `status`, `content`, `locations`, `rawInput`, `rawOutput`, `_meta` are optional. `toolCallId` is `ToolCallId` = plain `string`, "unique identifier for this tool call within the session", with **no format, pattern, prefix or length constraint**; `title` is a required human-readable string. Source: `schema/v1/schema.json` `$defs.ToolCall` (`required: ["toolCallId","title"]`) and `$defs.ToolCallId`; `https://agentclientprotocol.com/protocol/v1/tool-calls.md` Creating. Fetch 2026-11-18. **[PRIMARY]**
- **C6 — `name` is open to client/Agent shaping: optional, nullable, opaque, informational only.** Spec: "Names are opaque, informational metadata and do not advertise a capability or grant authorization"; ACP "does not define a naming or namespacing scheme"; Agent SHOULD include it on first report when available and SHOULD NOT change it later except to correct metadata. In v1 updates, omission or `null` both leave the old name unchanged (v1 cannot clear a name); string sets/replaces. RFD `tool-call-name.md` completed/stabilized 2026-09-17 for v1+v2, explicitly rejects putting the name in `_meta` or inferring it from `title`/`rawInput`. Source: `https://agentclientprotocol.com/protocol/v1/tool-calls.md` Creating/Updating; `https://agentclientprotocol.com/rfds/tool-call-name.md` Elevator pitch/What we propose/Wire semantics/FAQ/revision history; `https://agentclientprotocol.com/announcements/tool-call-name-stabilized.md` (indexed in llms.txt); `schema/v1/schema.json` `$defs.ToolCall.properties.name` + `$defs.ToolCallUpdate.properties.name`. Fetch 2026-11-18. **[PRIMARY]**
- **C7 — `kind` and `status` are closed enums in v1; `other`/`pending` are defaults.** `ToolKind` = `read|edit|delete|move|search|execute|think|fetch|switch_mode|other` (10 consts); `ToolCallStatus` = `pending|in_progress|completed|failed` (4 consts). Reference Rust SDK marks these fields `DefaultOnError`, so an unparseable kind/status falls back to default. v2 (Draft) permits custom tool kinds only when prefixed `_` and displays unknown non-underscore kinds as `other`; v1 offers no such sanctioned custom-kind channel. Source: `schema/v1/schema.json` `$defs.ToolKind`, `$defs.ToolCallStatus`; `agent-client-protocol-schema/src/v1/tool_call.rs` (`#[serde_as(deserialize_as = "DefaultOnError")]` on `kind`, `status`, `name`, `raw_input`, `raw_output`); `https://agentclientprotocol.com/protocol/v2/tool-calls.md` Reporting. Fetch 2026-11-18. **[PRIMARY]**
- **C8 — `ToolCallContent` is a fixed oneOf with three variants.** v1: `{type:"content", content: ContentBlock}`, `{type:"diff", ...}`, `{type:"terminal", ...}` (discriminator `type`). `ContentBlock` is itself a closed oneOf `text|image|audio|resource_link|resource` with fixed `type` consts. ACP content is a superset of MCP 2025-06-18 `ContentBlock` (extra optional `uri` on image) so MCP tool output can be forwarded unchanged. Source: `schema/v1/schema.json` `$defs.ToolCallContent`, `$defs.Content`, `$defs.ContentBlock`; `https://agentclientprotocol.com/protocol/v1/content.md` Content types. Fetch 2026-11-18. **[PRIMARY]**
- **C9 — v1 `ToolCallUpdate` requires only `toolCallId`; a permission request embeds that same update.** `session/request_permission` params require `sessionId`, `toolCall: ToolCallUpdate`, `options: PermissionOption[]`; option kinds are the closed set `allow_once|allow_always|reject_once|reject_always`. Client MAY auto-approve; Agent owns remembered decisions; Agents SHOULD NOT rely only on `title`/option `name` for automatic approval. Consequence: renaming a tool in `tool_call`/`name` carries no authorization semantics, but rewriting `toolCallId` or permission options can detach approval from the call. Source: `https://agentclientprotocol.com/protocol/v1/tool-calls.md` Updating/Requesting permission/Permission options/Security; `schema/v1/schema.json` `$defs.ToolCallUpdate` (`required: ["toolCallId"]`), `$defs.RequestPermissionRequest`. Fetch 2026-11-18. **[PRIMARY]**
- **C10 — ACP does NOT define tool schemas, tool definitions, `tools/list`, or `tools/call`.** First-party v1 schema has no defs matching tool schema concepts (def inventory contains only `ToolCall`, `ToolCallContent`, `ToolCallId`, `ToolCallLocation`, `ToolCallStatus`, `ToolCallUpdate`, `ToolKind`); direct string search of `schema/v1/schema.json` for `tools/list`, `inputSchema`, `toolSchema`, `ToolDefinition`, `tools/call` returned zero matches. ACP's own docs: MCP "gives an Agent tools and data"; the Client passes MCP servers to the Agent in `session/new`, and "A Client that wants to provide its own tools can expose them as an MCP server and include it in that list." Therefore tool name/description/inputSchema shaping is an **MCP-layer** concern, not an ACP field rename. Source: `schema/v1/schema.json` `$defs` keys + direct string search; `https://agentclientprotocol.com/get-started/related-protocols.md` Model Context Protocol; `https://agentclientprotocol.com/protocol/v1/session-setup.md` §MCP servers. Fetch 2026-11-18. **[PRIMARY]** (MCP spec internals not fetched in this angle — see Gaps.)
- **C11 — `session/new` fixed fields:** required `cwd` (absolute path) and `mcpServers` (array of stdio/http/sse server configs); optional `additionalDirectories`, `systemPrompt`, `_meta`. All Agents MUST support `session/new`, `session/prompt`, `session/cancel`, `session/update` at baseline; `loadSession` is capability-gated. `mcpServers` contains connection details only (name/command/args/env or type/url/headers) — no tool-name filtering or rewriting field exists in ACP. Source: `schema/v1/schema.json` `$defs.NewSessionRequest` (`required: ["cwd","mcpServers"]`), `$defs.McpServer`; `https://agentclientprotocol.com/protocol/v1/session-setup.md` Creating a session/MCP servers; `https://agentclientprotocol.com/protocol/v1/initialization.md` Session capabilities. Fetch 2026-11-18. **[PRIMARY]**
- **C12 — `_meta` is the sanctioned extension channel and is allowed on all the relevant types.** Type `{ [key: string]: unknown }`/`object|null`, `additionalProperties: true`; present on `NewSessionRequest`, `InitializeRequest/Response`, `SessionNotification`, `ToolCall`, `ToolCallUpdate`, `RequestPermissionRequest`, `Content` wrapper, capability objects. Spec says implementations "MUST NOT make assumptions about values at these keys"; `traceparent`/`tracestate`/`baggage` SHOULD be reserved for W3C trace context; custom method names MUST start with `_`; custom capabilities SHOULD use reverse-DNS keys like `com.example/<name>`. Crucially, "Implementations **MUST NOT** add any custom fields at the root of a type that's part of the specification" — so adding a top-level tool field is non-conformant; the same payload inside `_meta` is conformant transport but carries no guaranteed semantics. Source: `https://agentclientprotocol.com/protocol/v1/extensibility.md` §The `_meta` field/Extension methods/Advertising custom capabilities; `https://agentclientprotocol.com/rfds/meta-propagation.md` What we propose; `schema/v1/schema.json` `_meta` properties across the named defs. Fetch 2026-11-18. **[PRIMARY]**

The client-system-prompt RFD cites `claude-agent-acp`'s `_meta.systemPrompt` as a workaround and quotes the spec rule that implementations MUST NOT make assumptions about values at `_meta` keys. Source: `https://agentclientprotocol.com/protocol/v1/session-setup.md` §System prompt; `https://agentclientprotocol.com/rfds/client-system-prompt.md` Status quo/Design choices/Implementation details; `schema/v1/schema.json` `$defs.NewSessionRequest.properties.systemPrompt`, `$defs.SessionSystemPromptCapabilities`. ## Conflicting evidence

- **v1 vs v2 tool-call shape conflict is real but not applicable.** v1 has both `tool_call` and `tool_call_update` and cannot clear `name`; v2 has only `tool_call_update` upsert, nullable `name`, `_meta` patches. Resolved by C3: omp pins `protocolVersion: 1`, so v1 governs. Treat v2 guidance as non-authoritative for this path.
- **`_meta` tension, not contradiction.** Extensibility permits arbitrary `_meta` payloads (C12) while the client-system-prompt RFD says `_meta` is unsuitable for delivering instructions agents must act on (C13). Both are primary spec text: one is about wire legality, the other about semantic reliability. AgyHost (C14) sits on the legal-but-unreliable side.
- **Standard `systemPrompt` exists yet omp does not use it.** No evidence in the installed bridge that `agentCapabilities.sessionCapabilities.systemPrompt` is advertised by agy; if it is not, sending the standard field would be non-conformant (C13), which may explain the choice of `_meta`. This explanation is inference, not observed fact.
- **MCP `tools/list` vs ACP `session/new.mcpServers`.** ACP standard says clients provide tools via `mcpServers`; omp passes `[]` and relies on agy's `--ide-mcp-port` CLI bridge (C16). Both are first-party facts but describe different integration seams; no conflict in spec, only a divergence from the documented recommendation.
