# F — omp "signature" reaching the upstream model, and extension rewritability

Scope: what of `oh-my-pi` (omp) is visible to a provider's `streamSimple(model, context, options)`, and which of those surfaces an extension can transform without breaking the omp tool loop. Read-only investigation of the omp monorepo at the 18.18.6 snapshot (historical; the installed/host-verified build is 18.22.2 — see `F-antigravity-cli-source.md`), plus `omp://system-prompt-customization.md` and `omp://context-files.md`. Today 2026-11-18. No secret values quoted. Confidence noted per claim.

> Scope correction (2026-11-18): F3, F7–F9, Rewritable-surfaces items 4–6 and the Net paragraph below describe the **HTTP CCA** providers (`google-antigravity`, `google-gemini-cli`). On the primary `antigravity-cli` path (API `antigravity-acp`) omp emits no HTTP headers, User-Agent or Authorization header at all (`F-antigravity-cli-source.md:77`); `onPayload`/`onResponse` are set in provider options but never read, so `before_provider_request` and `after_provider_response` do not fire (`F-antigravity-cli-hooks.md:7,11,55`). Only `before_agent_start`, `context`/`input` and tool definitions/events are reachable there. See `F-antigravity-cli-hooks.md`.

## Findings

**F1. The visible surface count depends on the transport.** A provider sees (a) system-prompt text, (b) tool schemas/names, (c) the message/context stream including injected context files, skills and rules, (d) client metadata, (e) transport headers + request envelope, and (f) the `model`/`options` objects passed to `streamSimple`. The six-surface list is the HTTP-CCA case. On `antigravity-cli` there is no omp-controlled transport surface, so only prompt, tool schemas and messages are reachable for content shaping. (High confidence — direct code trace.)

**F2. The most literal omp marker is in the default system prompt.** `system-prompt.md` opens with `⁂ Role / You are omp's trusted coding assistant.` and injects `# Skills & Rules` (`Matching skill → MUST read \`skill://<name>\` first.`), `# Internal URLs`, `# Tool Inventory`, `# xd:// Tool Devices`, `⁂ Tool Policy`, delegation and workflow text, and RFC-2119 vocabulary. This block reaches the provider as `context.systemPrompt` (string[]). (High — `packages/coding-agent/src/prompts/system/system-prompt.md:1-90`.)

**F3. (HTTP CCA fallback/legacy only.) For `google-antigravity`, omp has *already* cloned the foreign client's wire signature — so "omp-specific" is mostly absent on the transport surface by design.** Evidence:
- User-Agent `antigravity/hub/<version> (aidev_client; os_type=…; arch=…; cl=1005016104)`, version auto-discovered from the official update manifest with a pinned fallback (`2.26.0`). (`packages/catalog/src/wire/gemini-headers.ts`, `getAntigravityUserAgent`, `DEFAULT_ANTIGRAVITY_VERSION`, `ensureAntigravityVersion`.)
- Headers: `Accept-Encoding: gzip` only, no explicit `Accept` (Bun adds `Accept: */*`), mirroring the native Go `net/http` client. (Same file, `getAntigravityHeaders`.)
- Request envelope built by `buildAntigravityRequestEnvelope`: `sessionId` signed decimal; `requestId = agent/<agentId>/<ts>/<trajectoryId>/<step>`; labels `cascade_id`, `root_cascade_id`, `request_id`, `trajectory_id`, `last_step_index`, `last_execution_id`, `model_enum`, `used_claude`, `used_claude_conservative`, `used_non_gemini_model`, inserted in alphabetical key order. Step counts user turns, model turns and tool results. Per-tier `modelEnum`, output cap and thinking config come from the serving account's discovered roster. (`packages/ai/src/providers/google-gemini-cli.ts:1235-1300`, `1380-1472`.)
- `VALIDATED` default tool mode; a forced-tool directive (`TOOL-ONLY TURN…`) is appended as a user message for Gemini when tool choice is `ANY`; no `anthropic-beta` Claude thinking header on Claude 5.x. (`google-gemini-cli.ts:1380-1420, 607-617`; `google-antigravity-forced-tool.md`.)
- Conclusion: the residual omp-specific signature for Antigravity is the *content* surfaces (prompt/tools/context), not headers or envelope. (High.)

**F4. Client metadata is also an imitation, and is provider-gated.** `buildSessionMetadata` emits `metadata.user_id` as a JSON string of `{session_id, account_uuid, device_id}` — documented as "shaped like real Claude Code's `getAPIMetadata` output". `account_uuid`/`device_id` are added **only** for `provider === "anthropic"`; all other providers (including Anthropic-format proxies) get `{session_id}` alone to avoid leaking Claude identity. `device_id` is derived from omp's persistent install id plus the Claude account UUID. Installed as a live resolver on Main, subagents and advisors via `agent.setMetadataResolver`. (`packages/coding-agent/src/session/session-metadata.ts:28+`; `agent-session.ts:6499-6520`; `packages/agent/src/agent.ts:702`.) (High.)

**F5. Tool names/schemas are visible and are largely stable OMP identifiers.** `BUILTIN_TOOL_NAMES` = `read, bash, edit, ast_grep, ast_edit, ask, debug, ida, eval, github, glob, grep, find, lsp, checkpoint, rewind, context_notes, new_context, security_scan, task, wait, todo, web_search, write, memory_edit, retain, recall, reflect, learn, manage_skill`; hidden: `yield, goal, think`. `read`/`write` double as the `xd://` transport (devices are mounted through them, not separate tool schemas). `ESSENTIAL_BUILTIN_TOOL_NAMES` pins core names to `loadMode: "essential"` so a re-registration cannot silently demote them. (`packages/coding-agent/src/tools/builtin-names.ts:1-40`, `essential-tools.ts:1-40`.) (High.)

**F6. Context files, skills and rules are injected into the provider-facing prompt.** Context files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `copilot-instructions.md`, `contextFiles.extra`) are expanded (`@` imports resolved) into a `<repo-rules>` block in the trailing `<project-context>` system block; sticky `RULES.md` is carried on every request as an always-apply rule; discovered skills become `<skills>` name+description lines. Task subagents drop `AGENTS.md` but keep `RULES.md`. (`omp://context-files.md`; `omp://system-prompt-customization.md`.) (High.)

**F7. `streamSimple` sees exactly `(model, context, options)`.** `context` carries `systemPrompt`, `messages`, `tools`; `options` (`SimpleStreamOptions`) carries `metadata`, `headers`, `providerSessionState`, `antigravityEndpointMode`, `onPayload`, `onResponse`, `onSseEvent`, etc. `SessionProviderBoundary.prepareSimpleStreamOptions` fills `metadata` from `agent.metadataForProvider(provider)`, sets `antigravityEndpointMode` for `google-antigravity`, and chains session/request payload hooks. (`packages/ai/src/stream.ts:1800-1838`; `packages/ai/src/types.ts:672-680`; `packages/coding-agent/src/session/session-provider-boundary.ts:226-250`.) On `antigravity-cli` the CLI transport sets `onPayload`/`onResponse` in options but ignores them, so those hooks do not fire there. (High.)

**F8. (HTTP CCA providers only.) `onPayload` runs *inside* the provider, after the Antigravity envelope is built and before `JSON.stringify`.** For Antigravity: `buildRequest(...)` → `await options?.onPayload?.(requestBody, model)` → optional replacement → `ensureAntigravityVersion` → headers from `getAntigravityHeaders()` plus `options.headers` → stringify. A payload hook can therefore rewrite `labels`, `request.sessionId`, `generationConfig`, tool declarations, and the system-prompt/message parts, but **cannot change headers** at that point. (`packages/ai/src/providers/google-gemini-cli.ts:580-623`.) (High.)

**F9. On HTTP CCA paths, main-session provider requests are routed through extension payload hooks.** For `google-antigravity` and `google-gemini-cli`, `sdk.ts` sets `onPayload = (payload, model, signal) => extensionRunner.emitBeforeProviderRequest(payload, model, signal)`, and the same `onPayload` is passed into `AgentSession` (sdk.ts:4848, 5186, 5739). Compaction side-requests also wire it (`session-maintenance.ts:3804-3808`). So on those HTTP paths `on("before_provider_request")` is the single broadest rewrite surface. On `antigravity-cli` the hook is wired into options but ignored by the CLI transport, so it is not a rewrite surface there. (`packages/coding-agent/src/sdk.ts:4717-4728`.) (High.)

## Rewritable surfaces

1. **System prompt — YES (extension).** `on("before_agent_start")` returning `{ systemPrompt: string[] }` replaces the whole generated block array for the next request and its continuations, chain-ordered across extensions (`runner.ts:2620-2678`, `agent-session.ts:9357`). Also file/CLI routes (`SYSTEM.md`, `SYSTEM_TEMPLATE.md`, `APPEND_SYSTEM.md`, per-model `systemPromptTemplates`) and, for SDK embedders only, `CreateAgentSessionOptions.systemPrompt` (full opaque replacement). **Loop risk:** tool *schemas* are still generated by the provider-facing session, so the loop stays mechanically intact, but dropping tool policy / internal-URL / `xd://` guidance from the prompt degrades reliable tool calling. Keep those sections when rewriting.

2. **Messages / context — YES (extension).** `on("context")` returning `{ messages }` runs as `transformContext` before `convertToLlm` (`sdk.ts:4647-4650`, `runner.ts:2530-2561`). **Loop risk:** low if tool-call/tool-result pairing is preserved; dropping tool results or splitting assistant tool-call turns breaks the loop. Runner preserves history-index bookkeeping for changed messages.

3. **Tool names / descriptions / schemas — YES (extension).** `registerTool()` adds or re-registers tools; re-registering a built-in name replaces its definition, and `defaultLoadModeForToolName` keeps essential names top-level. `tools:` allowlists can restrict the set. **Loop risk:** renaming/removing `read`, `write`, `bash`, `edit`, `task`, or the hidden `think` can break tool execution or make `xd://` devices unreachable.

4. **Provider request payload (including omp/Antigravity signatures) — YES (extension, broadest; HTTP CCA paths only, does not fire for `antigravity-cli`).** `on("before_provider_request")` returns a replacement payload; it is the session `onPayload` for all HTTP CCA chat requests (`sdk.ts:4717-4728`) and is invoked inside `google-gemini-cli.ts:602`. Can rewrite `labels` (cascade/request/trajectory/model_enum/used_*), `request.sessionId`, `generationConfig`, tool declarations, system/message parts, and Anthropic `metadata.user_id`. **Loop risk:** must preserve valid Cloud Code Assist schema, tool declarations and tool-call ids; otherwise the model cannot emit usable calls. Cannot alter headers here.

5. **Transport headers / User-Agent — NOT via the payload hook.** Reachable only by (a) `registerProvider(name, { headers, streamSimple, … })` with a custom stream implementation (full control, high cost: must reproduce `AssistantMessageEventStream`, auth, error mapping), or (b) environment overrides consumed by `gemini-headers.ts` (`PI_AI_ANTIGRAVITY_VERSION`, `_CL`, `_OS`, `_ARCH`, `PI_AI_GEMINI_CLI_VERSION`) — global, not per-request, and not an extension API. **Loop risk:** high for (a).

6. **Client metadata — NO direct ExtensionAPI setter, but rewritable indirectly (HTTP CCA paths only).** `before_provider_request` can replace `metadata.user_id` in the Anthropic body; SDK embedders can install `agent.setMetadataResolver`. Provider gating lives in `buildSessionMetadata`. **Loop risk:** low.

7. **Skills / rules / context files — indirectly YES.** They are prompt content, so `before_agent_start` system-prompt replacement can scrub them; config knobs (`disabledProviders`, `disabledExtensions: context-file:…`, `contextFiles.extra` from `omp://context-files.md`) control discovery. No dedicated per-extension API.

8. **Provider/model identity and endpoint — YES (extension/config).** `registerProvider(name, ProviderConfig)` (models, `api`, `streamSimple`, `headers`, `oauth`, `oauth.modifyModels`), `on("before_subagent_spawn")` for model patterns; `antigravityEndpointMode` via settings (`cfgProvidersAntigravityEndpoint`) rather than an extension API.

**Net:** the payload-hook lever applies to HTTP CCA paths; on the primary `antigravity-cli` path the reachable loop-safe set is {system prompt, messages, tool descriptions}, and header/envelope imitation is owned by `agy`. The hard/unsafe set on the HTTP paths is {headers/User-Agent, live per-request metadata resolver, model/transport internals}.

## Open questions

- **O1.** On `antigravity-cli` the answer is no — `before_provider_request` does not fire (the CLI transport ignores `onPayload`/`onResponse`; `F-antigravity-cli-hooks.md:7,55`). On HTTP side requests (compaction, direct `google-antigravity`, judges) it remains unverified for image generation.
- **O2.** Exact `CloudCodeAssistRequest` wire shape at the `onPayload` seam. Observed return of `buildRequest` is `{ project, requestId, request, model, userAgent }` with `request.labels` and `request.sessionId`; full field inventory needed before rewriting labels safely.
- **O3.** How `context.systemPrompt` is folded for `google-gemini-cli` (`normalizeSystemPrompts`) — separate `contents` roles vs. a leading user message — and whether prompt-cache prefixes are invalidated by rewrites.
- **O4.** Persistence of a `before_agent_start` system-prompt override across prompt-cache rebuilds, `/model` and role switches, and retry-fallback hops (docs say "until the next preparation").
- **O5.** Whether any upstream detector actually inspects prompt text/tool names (the content surfaces) versus the transport/telemetry fingerprint. Scrubbing omp's prompt markers is only speculative mitigation; no evidence found that Antigravity/Google reads prompt text for client identification.
- **O6.** Whether omp's persistent install id (`getInstallId()`) is observable by any provider other than through Anthropic `device_id` (appears gated, but not exhaustively traced).
- **O7.** Whether the auto-updater manifest lookup (`User-Agent: electron-builder` to `antigravity-hub-auto-updater-…`) is itself a fingerprintable omp-side call; appears benign and cached, unverified against a live capture.
